# OpenBikeNet Protocol v0: Shared Presence

**Status: draft.** v0 may still change in breaking ways until it is marked stable. Feedback is
welcome in [Discussions](../../../discussions).

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## 1. Scope

v0 lets indoor cycling apps show each other's riders on shared routes. Each app keeps its own
physics and reports where its riders are. The server keeps the current state and passes it on.

v0 covers:

- a WebSocket connection between an app and a server,
- shared routes defined as a 1D elevation profile,
- joining, updating and leaving riders on a route,
- self-declared app identification and public usage statistics.

Not in v0: server-side physics, accounts, private rooms with access control, races and events,
proof of app ownership, other transports such as MQTT. The message format does not depend on
WebSocket, so other transports can be added later.

## 2. Terms

- **App:** an indoor cycling application that implements this protocol.
- **Connection:** one WebSocket connection from an app instance to a server. It MAY carry many
  riders. Apps with a backend SHOULD connect from the backend and carry all their riders over one
  connection. Apps without a backend connect from the client, usually with one rider.
- **Rider:** one person riding. A rider is on at most one route at a time.
- **Route:** a shared route as defined in section 4.
- **Room:** a group of riders on the same route who see each other. The default room is `public`.

## 3. Connection

### 3.1 Endpoint

Servers accept WebSocket connections at the path `/v0`, for example
`wss://<host>/v0`. Public servers MUST use `wss`. A later incompatible version gets a new path
(`/v1`), and a server MAY serve both.

### 3.2 Frames

Every message is one WebSocket text frame holding one JSON object with a string field `type`.
Binary frames are not used, and a server MUST close the connection if it receives one.

Receivers MUST ignore unknown fields. A server MUST answer an unknown `type` with an
`error` (`unknown_type`). An app MUST ignore a server message with an unknown `type`, and MUST
accept unknown values of `error.code` (acting on `fatal`) and of `left.reason`. This lets new
optional fields, server messages, error codes and leave reasons be added without a new version.

Any message from an app MAY carry a string field `ref` (at most 64 characters). If the server
answers that message with an `error`, the error carries the same `ref`.

### 3.3 Units

| Quantity | Unit | JSON type |
|---|---|---|
| distance, length, elevation | metres | number |
| speed | metres per second | number |
| power | watts | integer |
| cadence | revolutions per minute | integer |
| heart rate | beats per minute | integer |

### 3.4 Lifecycle

1. The app opens the connection and MUST send `hello` as its first message, within 10 seconds.
2. The server answers with `welcome`.
3. The app sends `subscribe` for each route and room whose riders it wants to see, and receives a
   `snapshot` for each.
4. The app sends `join` for each of its riders, then `update` messages while they ride, and
   `leave` when they stop.
5. The server sends `joined`, `updated` and `left` for riders of other connections in the routes
   and rooms the app has subscribed to.

Subscribing and joining are independent. An app can watch a route without riders on it, and it
can put riders on a route without watching it.

### 3.5 Keepalive and disconnect

The server sends a WebSocket ping at least every 15 seconds. If no pong arrives within 30
seconds, the server closes the connection.

An app can check that the server is still there with `ping` (section 6.6), which the server
answers with `pong` (section 7.7). An app that has received nothing for 20 seconds SHOULD send a
`ping`, and MAY treat the connection as closed if nothing arrives within the next 10 seconds.
An app that can see WebSocket pings MAY instead treat the connection as closed when no ping has
arrived for 45 seconds.

When a connection closes, all of its riders leave with reason `disconnect`. An app that
reconnects MUST send `hello`, `subscribe` and `join` again. Its riders get new server IDs.

Apps SHOULD reconnect with exponential backoff (for example 1 s, 2 s, 4 s, up to 60 s).

## 4. Routes

### 4.1 Route files

Shared routes are published in this repository as `routes/<id>.json` and validated by
[`schemas/route.schema.json`](../schemas/route.schema.json).

```json
{
  "id": "velodrome-250",
  "name": "Velodrome 250 m",
  "length": 250,
  "loop": true,
  "profile": [[0, 0], [250, 0]]
}
```

| Field | Meaning |
|---|---|
| `id` | stable route ID, `^[a-z0-9][a-z0-9-]{1,63}$` |
| `name` | display name |
| `length` | route length in metres, greater than 0 |
| `loop` | `true` if the end of the route joins its start |
| `profile` | list of `[distance, elevation]` points in metres |

Rules for `profile`:

- The first point has distance 0 and the last point has distance `length`.
- Distances strictly increase.
- Elevation between two points is linear interpolation. The gradient between two points is the
  elevation difference divided by the distance difference.
- On a loop, the first and last elevation MUST be equal.

A route describes only distance and elevation. Geometry, curves, banking, width and scenery are
up to each app. A rider at the same distance is at the same spot on the route in every app.

### 4.2 Route identity

A published route file MUST NOT change. A changed route is published under a new ID, for example
`velodrome-250-v2`.

### 4.3 Position

A rider's position is given by two fields:

- `distance`: metres from the start of the route, `0 ≤ distance < length`. On a loop, the
  distance goes back to 0 when the rider crosses the start line.
- `lap`: number of laps the rider has finished since joining, an integer ≥ 0. On a route that is
  not a loop, `lap` is always 0.

Apps place riders by `distance`. `lap` is extra information, for example for a leaderboard.

On a route that is not a loop, a rider who reaches the end SHOULD leave.

### 4.4 The first route

`velodrome-250` is a flat 250 m loop. It is the first shared route because every app can build
it the same way.

## 5. App identification

An app identifies itself in `hello` with an app ID, for example `openradlr`. The ID:

- matches `^[a-z0-9][a-z0-9-]{1,31}$`,
- is chosen by the app's developers and SHOULD be the app's name,
- needs no registration, approval or secret.

The ID is a claim, not proof. Servers use it for statistics and show it with each rider, so
users can see which app a rider uses. Servers MUST NOT use it to grant access.

To avoid two apps choosing the same ID, developers SHOULD add their app to
[`apps.md`](../apps.md) with a pull request. The list is for discovery only, and servers do not
check it.

## 6. Messages from the app

### 6.1 `hello`

```json
{"type": "hello", "app": {"id": "openradlr", "version": "0.3.1", "name": "OpenRadlr", "url": "https://openradlr.com"}}
```

| Field | Required | Meaning |
|---|---|---|
| `app.id` | yes | app ID (section 5) |
| `app.version` | yes | app version, free text, at most 32 characters |
| `app.name` | no | display name of the app, at most 32 characters |
| `app.url` | no | website of the app, at most 200 characters |

`hello` MUST be sent exactly once. A second `hello` gets the error `hello_repeated`.

### 6.2 `subscribe` and `unsubscribe`

```json
{"type": "subscribe", "route": "velodrome-250", "room": "public"}
{"type": "unsubscribe", "route": "velodrome-250", "room": "public"}
```

`room` is optional and defaults to `public`. It matches `^[a-z0-9][a-z0-9-]{0,31}$`.

After `subscribe` the server sends a `snapshot` of the room, then `joined`, `updated` and `left`
for that room until `unsubscribe` or disconnect. Subscribing twice to the same route and room has
no effect beyond a new `snapshot`.

Apps SHOULD use the room `public`. In v0 any valid room name works the same way. Room names are
not secret and give no privacy.

### 6.3 `join`

```json
{"type": "join", "rider": "u-1842", "route": "velodrome-250", "room": "public", "name": "Anna",
 "lap": 0, "distance": 0, "speed": 0}
```

| Field | Required | Meaning |
|---|---|---|
| `rider` | yes | the app's own ID for this rider, 1 to 64 characters, unique within the connection |
| `route` | yes | route ID |
| `room` | no | room, default `public` |
| `name` | yes | display name, 1 to 32 characters (section 6.3.1) |
| `lap`, `distance`, `speed`, `power`, `cadence`, `heart_rate` | as in `update` | the starting state |

The state in `join` does not count towards `max_update_hz`: an app MAY send an `update` for the
rider right after its `join`.

The server never shows the app's `rider` value to other apps. Apps SHOULD NOT use personal data,
such as an e-mail address, as the rider value.

A rider that has already joined MUST leave before it joins again, on the same or another route.

#### 6.3.1 Display names

A character is a Unicode code point. A name MUST NOT:

- contain a character of the Unicode general categories Cc (control), Cf (format), Co (private
  use), Zl (line separator) or Zp (paragraph separator), except U+200D ZERO WIDTH JOINER, which
  emoji sequences need,
- consist only of whitespace (characters with the Unicode property `White_Space`).

This keeps out invisible characters and bidirectional overrides, which would let a rider hide or
reverse their name in other apps. Servers answer such a name with `invalid_value`. Receivers MUST
display names as plain text, never as markup.

### 6.4 `update`

```json
{"type": "update", "riders": [
  {"rider": "u-1842", "lap": 3, "distance": 112.4, "speed": 11.8, "power": 245, "cadence": 92, "heart_rate": 151},
  {"rider": "u-2077", "lap": 1, "distance": 20.0, "speed": 9.6}
]}
```

| Field | Required | Range |
|---|---|---|
| `rider` | yes | a joined rider of this connection |
| `lap` | yes | integer, ≥ 0 |
| `distance` | yes | `0 ≤ distance < length` of the route |
| `speed` | yes | 0 to 30 |
| `power` | no | integer, 0 to 3000 |
| `cadence` | no | integer, 0 to 250 |
| `heart_rate` | no | integer, 20 to 250 |

One `update` carries any number of riders of the connection, on any routes. Apps SHOULD send
each rider about once per second and MUST NOT send a rider more often than `max_update_hz`
(section 9).

The server checks each rider entry on its own. An invalid entry is dropped and answered with an
`error`. The other entries of the message still apply.

If the server receives no update for a rider for `rider_timeout_s` seconds (section 9), the
rider leaves with reason `timeout`.

### 6.5 `leave`

```json
{"type": "leave", "rider": "u-1842"}
```

The rider leaves its route with reason `leave`.

### 6.6 `ping`

```json
{"type": "ping", "ref": "hb-17"}
```

The server answers with `pong` (section 7.7). See section 3.5 for when to send it.

## 7. Messages from the server

Remote riders are identified by an `id` the server assigns. It is at most 16 characters, unique
on the server, and not reused while the server runs. A server does not send an app its own
riders.

### 7.1 `welcome`

```json
{"type": "welcome", "protocol": "0.2", "connection": "c9Qe4",
 "limits": {"max_update_hz": 4, "rider_timeout_s": 10, "max_riders": 200, "max_subscriptions": 16, "max_message_bytes": 65536}}
```

`protocol` is the minor version of v0 the server implements. `connection` is the server's ID for
the connection, useful when reporting problems.

### 7.2 `snapshot`

```json
{"type": "snapshot", "route": "velodrome-250", "room": "public", "riders": [
  {"id": "r7Kx2", "app": "incyclist", "name": "Ben", "lap": 5, "distance": 201.3, "speed": 12.1, "power": 260}
]}
```

All riders in the room from other connections, with their latest state.

### 7.3 `joined`

```json
{"type": "joined", "route": "velodrome-250", "room": "public",
 "rider": {"id": "r7Kx2", "app": "incyclist", "name": "Ben", "lap": 0, "distance": 0, "speed": 0}}
```

### 7.4 `updated`

```json
{"type": "updated", "route": "velodrome-250", "room": "public", "riders": [
  {"id": "r7Kx2", "lap": 5, "distance": 213.4, "speed": 12.1, "power": 262}
]}
```

The server passes each `update` on without delay. A server MAY combine updates of several
riders into one `updated` message. Optional fields appear only if the app sent them.

Apps SHOULD interpolate remote riders between updates so they move smoothly.

### 7.5 `left`

```json
{"type": "left", "route": "velodrome-250", "room": "public", "id": "r7Kx2", "reason": "timeout"}
```

`reason` is `leave`, `timeout` or `disconnect`.

### 7.6 `error`

```json
{"type": "error", "code": "invalid_value", "message": "distance must be below 250", "ref": "42", "rider": "u-1842", "fatal": false}
```

| Field | Meaning |
|---|---|
| `code` | one of the codes below |
| `message` | text for developers, not meant for users |
| `ref` | the `ref` of the message that caused the error, if it had one |
| `rider` | the app's rider value, if the error is about one rider |
| `fatal` | `true` if the server closes the connection right after this message |

| Code | Fatal | When |
|---|---|---|
| `hello_required` | yes | the first message was not `hello`, or no `hello` arrived in 10 seconds |
| `hello_repeated` | no | a second `hello` |
| `invalid_message` | no | not valid JSON, missing or wrong field |
| `unknown_type` | no | unknown `type` |
| `invalid_app_id` | yes | `app.id` does not match the format |
| `unknown_route` | no | the route does not exist on this server |
| `invalid_room` | no | the room does not match the format |
| `rider_exists` | no | `join` for a rider that has already joined |
| `unknown_rider` | no | `update` or `leave` for a rider that has not joined |
| `invalid_value` | no | a value is out of range |
| `rate_limited` | no | a rider was sent more often than `max_update_hz`; the entry is dropped |
| `limit_exceeded` | no | `max_riders` or `max_subscriptions` reached |
| `message_too_large` | yes | a message is larger than `max_message_bytes` |
| `too_many_errors` | yes | the connection keeps causing errors; `rate_limited` does not count |

### 7.7 `pong`

```json
{"type": "pong", "ref": "hb-17"}
```

The answer to `ping`. It carries the `ref` of the `ping`, if it had one.

## 8. Usage statistics

Servers SHOULD publish usage per app ID as JSON at `GET /v0/stats` (plain HTTPS, same host):

```json
{"apps": [
  {"id": "openradlr", "versions": ["0.3.1"], "connections": 1, "riders": 4,
   "first_seen": "2026-11-20", "last_seen": "2026-11-21", "rider_minutes_30d": 812}
]}
```

| Field | Meaning |
|---|---|
| `versions` | app versions seen in the last 30 days |
| `connections`, `riders` | open connections and riders right now |
| `first_seen`, `last_seen` | UTC dates of the first and the most recent connection |
| `rider_minutes_30d` | minutes ridden by riders of the app in the last 30 days |

## 9. Limits

Servers announce their limits in `welcome`. Recommended values:

| Limit | Value |
|---|---|
| `max_update_hz` per rider | 4 |
| `rider_timeout_s` | 10 |
| `max_riders` per connection | 200 |
| `max_subscriptions` per connection | 16 |
| `max_message_bytes` | 65536 |
| open connections per IP address | 10 |

## 10. Privacy

- Riders are shown to others by display name only. Apps SHOULD let riders choose this name and
  SHOULD NOT send full real names without the rider's consent.
- Servers MUST NOT store display names, rider values, positions or IP addresses beyond what the
  running connections need. Only the per-app statistics of section 8 are stored.
- Power, cadence and heart rate are optional. Apps SHOULD let riders turn off sharing them.
